## 1. 所感への回答

### 1-0. 先に確認したいこと（利用側へ）

- 「100 を超える質問」の内訳: 第 1 回／第 2 回以降の件数、必須／任意、高影響、空欄（仮回答採用）にした件数。質問票冒頭の「進捗: 回答 n / N」と `python tools/questionnaire.py stats requirements/questionnaire.md` で出る。
- 任意の質問を「空欄＝仮回答どおり」で飛ばせることをご存じだったか。この案内は質問票テンプレート（`questionnaire.py template`）には無く、エージェントが指示に従って冒頭に書き足す仕組み（今回の実走では書かれていた。§5-2）。出力ごとに揺れ得るので、お手元の質問票に無かった可能性がある。本体側の過去計測でも同じ事象（任意 47 問を全部手書き）が記録されている。
- 質問票ファイルそのものを共有いただけると、分類・種別ごとの負荷を数字で見られる。

根拠: tools/questionnaire.py TEMPLATE（冒頭文）、.github/skills/requirements-elicitation/SKILL.md 手順 7、.github/agents/requirements.agent.md 手順 3（D099 注記）

### 1-1. 質問が終わらない。スケジュールの見通しが立たない

【現状】
- 設計思想は「問数は減らさず厚く聞く」（Spec Kit の 5 問上限は不採用。D098 決定 2）。要件定義は「人が最も関わるフェーズ」と位置づけ、設計以降を人の手を最小限にするための投資と考えている。
- 進め方: /01 が被覆表（11 分類ごとに Clear / Partial / Missing）を作り、Partial / Missing の分類だけを第 1 回として一括で出す。/02 が回答を読み、追加質問が要るときだけ「第 N 回」を同じファイルに追記する。本体の計測（todo-app）では第 1 回 76 問 → 第 2 回 8 問。今回の実走（§5）では 85 → 3（回答の矛盾） → 5（独立レビューの指摘から派生） → 2 の 4 回。
- フェーズを閉じる条件は 3 つ: (1) 必須の未回答ゼロ、(2) 独立レビュアー spec-critic の BLOCKER / MAJOR 解消、(3) 人の承認「この内容で要件定義完了としてよいですか」。未回答の必須を残したまま承認した場合は「後で」として台帳に記録され、承認は止まらない（実走で確認）。

【ギャップ】
- 回数の上限、被覆率による終了判定、「あと何回で終わる」の見通し表示が無い。被覆表は持っているのに、利用者には残件として見せていない。
- 第 2 回以降の質問が「前回回答から派生したもの」に限定されておらず、新規分類の質問が増え得る。

【対策】
- 質問票冒頭に「終了見通し」欄: 被覆表の残件（Partial / Missing の分類数）、原則 2 回で閉じる旨、3 回目以降は理由を明示。
- 第 2 回以降は「前回回答の派生」に限定し、新規論点は未確定事項として台帳に送る（質問ではなく前提として扱う）。

根拠: requirements-elicitation/SKILL.md 60-120、requirements.agent.md 34-68、DECISIONS.md D098、evaluation/results/elicitation/todo-app-01-20260923.json

### 1-2. 回答候補と推奨を提示してほしい

【現状】
- 質問は「記述 / 単一選択 / 複数選択」の種別を持ち、選択式には選択肢が付く。記述式には「仮回答」（memo と探索から AI が書いた理解の下書き）が付き、「仮回答どおり」と書くか直すだけで済む。任意は空欄なら仮回答を採用し、/02 が採用一覧を提示する。
- 「高影響」（デプロイ先・自動化境界・データ削除・認証・費用・法規・スコープ外）には、黙従（AI 案の丸呑み）を防ぐため意図的に仮回答を付けない。`questionnaire.py check` が高影響への仮回答を ERROR にする（実機確認済み）。実走（§5-2）では 85 問中 40 問が高影響で、うち 36 問には選択肢が付き、記述式の 4 問は候補なしだった。

【ギャップ】
- 「推奨」の独立した表示が無い（仮回答が兼ねる）。選択式で推奨を先頭に置く規定も無い。所感の「推奨も記載してほしい」はここに当たる。
- 高影響の記述式は「候補も推奨も無い」。設計意図は「推奨を付けない」であって「候補を出さない」ではないので、候補の列挙は可能。
- 「空欄＝仮回答どおり」の案内がテンプレートに無く、エージェント任せ（1-0）。

【対策】
- 全質問に「推奨: ○○（理由 1 行）」。高影響は「候補は並べるが推奨は付けない」。候補外は自由記述で受ける（ご提案どおり）。
- テンプレート冒頭文に「任意は空欄で仮回答どおり。必須だけ書けばよい」を追加。

根拠: requirements-elicitation/SKILL.md 67-96、tools/questionnaire.py check()（高影響 ERROR・記述式の仮回答なし WARN）

### 1-3. 質問の内容が長く、回答コストが高い

【現状】
- 1 問が「分類・種別・根拠・反映先・仮回答・回答」の 6 行構造。100 問なら 600 行超。根拠と反映先は AI 側の追跡用（なぜ聞くか・どこへ書くか）で回答者が読む必要は無いが、同じ段に並ぶため読み飛ばせない。
- 「1 問 1 論点」「探索で分かることは聞かない」「検証不能な問いを出さない」の規律はあるが、質問文の長さの上限は無い。

【対策】
- 回答者向け行（質問文・選択肢・推奨・回答欄）と AI 向け行（根拠・反映先）を分け、後者は末尾の付録へ。質問文は 1〜2 文に制限。
- 必須と高影響だけを集めた「まず答える 20 問」を先頭に置き、残りは「空欄でよい任意」と見出しで示す。
- 短答で済む確認はチャット（1 往復 5 問まで）の既存経路に寄せる。

根拠: requirements-elicitation/SKILL.md 67-75（質問の形）、127-138（チャットで聞いてよい場合）

### 1-5. 保留した回答は後からどう吸収されるか

【現状】（実機確認済み）
- 「後で」「保留」は予約語。必須なら /02 がその項目だけをチャットで個別確認する（check が WARN で列挙）。任意なら仮回答を採用し、`requirements.md` §7「未確定事項（前提・リスク台帳）」に A-nnn 行（種別: 前提、確認期限: 設計フェーズ着手前）として記録される。「わからない」はリスク行。
- 後から回答が来たら質問票に「第 N 回」として追記し、反映先の節を更新する。設計エージェントは着手前に §7 を点検し、設計判断に直結する未確定があれば要件定義へ差し戻す。

【ギャップ】
- A-nnn を「解消済み」にする正式手順と状態列が無く、台帳に残り続ける。仮回答が無い任意質問が空欄のままだと「仮回答なしを採用」という空の前提行ができる（実機確認）。
- 実走では台帳が 52 行になり、うち 38 行は「仮回答を採用・確認済み」の記録で、人が見るべき未決 14 行（リスク 6・エージェントの推測で置いた前提 8）が埋もれた（§5-2）。

【対策】
- 台帳に状態列（open / 解消 / 設計へ持ち越し）と解消手順を追加。仮回答の無い任意質問は空欄採用を禁止（必ず候補を付けるか必須にする）。

根拠: tools/questionnaire.py classify_answer / ledger_rows、design.agent.md 23-37、requirements_template.md §7

### 1-6. 矛盾した回答の整合性チェックと、遡っての仕様変更

【現状】
- 機械検査は「同じ質問文の再出題」（回答済みの再出題は ERROR、未回答の再掲は WARN。実機確認）と ID の参照整合（trace-check）だけ。意味的な矛盾は検査しない。
- 矛盾の検出は spec-critic（別コンテキストの独立レビュアー）が担う。要件定義完了の前に必ず 1 回、前提が大きく変わったときはもう 1 回。観点は「ストーリー間・機能要件と NFR・スコープとスコープ外の矛盾」「仮回答どおりで確定した項目と他記述の食い違い（MAJOR）」。指摘と対応は要件書の未確定事項節の下に残る。
- 承認後の遡及は「差分駆動」: 要件 ID → 設計のトレーサビリティ表 → タスク → テストケース → 実コードの順に影響範囲を辿り、該当フェーズだけ再ゲートする。全フェーズのやり直しはしない。承認済み文書を編集するとフック（warn-stale-gate）が後続フェーズとの整合確認を警告する。
- 評価装置では「memo に仕込んだ矛盾（月末締め／25 日締め）が解消され、決定が記録されるか」を合否条件にしており、矛盾解消は設計上の要求事項。
- 実走（§5）では、memo の矛盾を /00 と /01 の両方が検出して必須質問にし、回答同士の矛盾は /02 が回答を読み込む段階で 3 件（仕込んだ 2 件＋意図しない 1 件）すべて検出して選択式で再確認した。文書作成後の spec-critic も BLOCKER 1 件（締め後の扱いの矛盾）を検出した。検出は 2 段で働くが、回答読み込み時の検出は指示層に明文化されておらず機械保証ではない。

【ギャップ】
- 「後の回答が前の回答を覆す」ときの優先規則と上書き理由の記録が未定義。spec-critic は終盤 1 回なので途中の往復で生じた矛盾は最後まで検出されない。

【対策】
- 第 N 回の回答を取り込むときに「同じ反映先に異なる値」を機械検査して WARN し、上書き時は旧値と理由を質問票に残す。
- 変更前に影響範囲（どこまで戻るか）を一覧で提示して承認を取る様式を、要件フェーズ内の差し戻しにも適用する。

根拠: spec-critic.agent.md 22-40、tools/questionnaire.py check()、AGENTS.md「差分駆動の原則」、change-request/SKILL.md 45-62、evaluation/tasks/expense-webapp/task.md

### 3. テスト（/07）

【現状】
- /07 は要件の受け入れ条件（Given / When / Then）と architecture.md から導出し、各ケースに要件 ID を必ず紐づける。コードからの導出は手順に無い（着手前に既存コード・既存テストの読み取り調査はする）。実装中はタスク担当が単体テストを書く。
- /07 は実装完了後に動き、作成後は確認を求めず /08 へ自動継続（実装〜テストは「全自動区間」）。人が関わるのは仕様解釈が割れたときと、reviewer の BLOCKER が解消しないときだけ。
- ディシジョンテーブル: 無い。状態遷移: 設計で「複雑な場合に状態遷移図」、テスト観点に 1 行あるだけで表の成果物は無い。
- トレーサビリティ: テスト計画の各表に「対応要件 ID」列。`trace-check.py` は「どこからも参照されない要件」「実在しない ID の参照」を検査するが、「テストで覆われていない要件」は検出できない（設計から参照されていれば OK）。要件×ケースの双方向マトリクスは作らない。/07 は trace-check を呼ばない（呼ぶのは /13-converge だけ）。

【対策】（採用価値が高い）
1. /02: 条件分岐を持つ要件（料金・権限・締め処理など）に決定表を付け、要件承認の対象に含める。
2. /04: 状態を持つ画面・エンティティの状態遷移表を詳細設計の必須項目にし、設計承認の対象に含める。
3. /05 の直後にテストケース草案を作る（/07 を実装前へ前倒し）。決定表の各行・状態遷移表の各セルからケースを機械的に起こす。
4. `trace-check.py` に「テスト未カバー要件」検査を追加し、要件×ケースのマトリクスを生成。AI が漏れを指摘し、人は「テスト設計の承認」1 回で確認する。
- 全自動区間の思想は維持し、人の確認は「テスト設計の承認」の 1 回に集約する。

根拠: prompts/07、test.agent.md 23-45、.github/skills/test-case-design/SKILL.md、tools/trace-check.py、docs/04-test/test_plan_template.md

### 4-1. 既存システムのリプレース案件への対応

【現状】
- 既存システム向けの入口は `/11-brownfield-intake`: 既存コードから as-is の要件・アーキテクチャ・環境・テスト計画を逆起こし（to-be は混ぜない。触る領域と背骨に絞る）→ spec-critic と横断整合監査で「文書にあるが実在しない機能・文書化漏れ」を潰す → 人の承認でゲート初期化 → 以後は `/12-change-request`（差分駆動）と `/13-converge`（docs と実装の乖離検出）で運用。/00 は既存コードを検知すると /11 へ誘導する。
- ご列挙の 8 ステップとの対応:
  - 現行ソースの解析 → あり（/11 手順 2・4）
  - 現行ソースと現行仕様書の差異抽出 → 一部。突き合わせ相手は逆起こしした as-is 文書で、既存の設計書・仕様書（Word / Excel 等）を読み込んで比較する手順は無い。
  - 最新仕様書の整備 → あり（as-is として新規生成。既存仕様書を埋める形は未対応）
  - 要件定義書への影響点整理・反映判定 → あり（/12 の影響範囲追跡。ハーネス形式の docs ができた後が前提）
  - 最新ソースと要件定義書の抜け漏れチェック → あり（/13 と trace-check）
  - 新旧テスト仕様書の比較、テスト仕様書と要件定義書のテスト範囲漏れ → 無い（/11 は既存テストの棚卸しと 1 回実行まで）
- 前提の違い: /11 は「既存コードを引き継いで改修し続ける」想定。「新システムで置き換える（リプレース）」型の手順は無い。

【対策】
- 「リプレース入口」を新設: 既存設計書の取り込み（Word / Excel / PDF → Markdown）→ 現行ソースとの差異抽出 → 最新仕様書 → 新要件への影響整理 → 新旧テスト仕様の比較、の流れを /11 の派生として定義。
- 利用側で Claude に既存設計書を読ませて差分比較している実践はこの手順の原型。/10-retrospective の 4 点セット（対象・問題・提案・根拠）で共有いただければ本体に取り込む。

根拠: .github/skills/brownfield-intake/SKILL.md、tools/intake-app.py、orchestrator.agent.md 手順 0、change-request/SKILL.md、converge/SKILL.md、audits/PROPOSALS.md（brownfield の open 提案 0 件）

## 3. 想定 Q&A 集（所感から読み取れる使い方・背景に基づく）

利用側の背景: 既存システムのリプレース案件、Excel で回る業務、複数人の回答者、md 成果物を工程ごとに検収する文化、Claude を既存設計書の差分比較に既に活用。

### 進め方・要件定義

**Q1. 質問票を複数人で分担して回答できるか。**
できる。質問票は 1 つの md ファイルで、分類ごとに見出しが分かれているので分類単位で担当を割り当てられる。ただし担当列・状態列は無い。分担する場合は冒頭に担当表を追記するか、Excel 書き出し（§2-2 C）を待つ。回答の記録は必ずこのファイルに戻す（チャットで答えた分も転記される）。

**Q2. 回答を数週間止めても大丈夫か。**
大丈夫。/02 は会話履歴ではなく質問票ファイルだけを読む設計なので、別の日・別のチャットで再開できる。再開は新しいチャットで `/02-requirements-deepdive`。

**Q3. memo（要件メモ）にはどこまで書けばよいか。**
書くほど質問が減る。質問票は「memo と探索で分かること」を質問しない規律なので、既存資料・業務フロー・画面一覧・制約（環境・権限・締め処理）を memo に貼るか参照パスを書く。被覆表で Clear になった分類は質問されない。

**Q4. 要件定義にどのくらい時間と費用がかかるか。**
本体の計測（小規模 todo-app）では /01 が約 18 分・$6、/02 累積 $16、人の回答 15 分。業務システムではこの数倍。費用は会話ごとの受領書（`/99-status` の費用欄）で見られる。

**Q5. 要件定義の「承認」は誰が何を見て行うか。**
requirements.md（ユーザーストーリーと受け入れ条件）・nfr.md・environment.md・未確定事項台帳。見るべきは「スコープ外が書かれているか」「高影響の項目を自分で決めたか」「未確定事項に設計を左右するものが残っていないか」。詳細な文言の検証は spec-critic が済ませている。

**Q6. 承認後に要件を変えたくなったら。**
構築中なら該当フェーズへ差し戻し（要件なら /02）。運用中なら `/12-change-request`。どちらも影響範囲をトレーサビリティ表から辿って該当部分だけ再ゲートする。全部やり直しにはならない。

### 設計・画面

**Q7. 画面デザインは誰が決めるか。デザイナーの成果物を使えるか。**
設計フェーズで AI が HTML モックを作り、人が目視で直す。既存のデザイン（Figma・画面仕様書）があれば memo か docs に置けば参照される。Figma との自動連携は無い。

**Q8. 設計書が膨大で読めない。どこを見ればよいか。**
§1-5 の 4 点（技術スタックと ADR・コンテキスト図・NFR 実現方法・要件対応表）。残りは spec-critic の指摘と対応結果を読む。設計は「AI が決め、人は最終承認 1 回」の設計。

**Q9. 技術スタックは指定できるか。社内標準に縛れるか。**
できる。memo か environment.md に必須技術・禁止技術を書けば制約として扱われる。設計フェーズで候補提示があるときに選ぶ。社内規約は `stack-conventions` スキルとして案件側で作り、再利用できる。

### 実装・テスト

**Q10. 実装中は本当に何も見なくてよいのか。**
設計承認後からテスト完了までは全自動区間。止まるのは、要件・設計から判断できない事実が要るとき、同一タスク 3 回失敗、push・デプロイ等の外部反映、environment.md で「人手」に分類した作業。完了は自己申告でなく証拠（テスト実行ログ等）で判定し、10 タスクごとに独立レビューが入る。

**Q11. 既存のテスト仕様書の形式（Excel のテスト項目書）で出せるか。**
docs/04-test/test-plan.md（Markdown 表）が正。Excel への変換は案件側のスクリプトで可能だが、正は md のまま（AI が読む）。形式の変更は本体の対策（§1-3）に含める。

**Q12. テストの網羅性は誰が保証するか。**
現状は AI（要件 ID 紐づけ＋観点チェックリスト）と reviewer。人の承認工程は無い。§1-3 の対策で「テスト設計の承認」を 1 回入れる。

### 既存システム・リプレース

**Q13. 既存の設計書（Word / Excel）を読ませられるか。**
現状、ハーネスの手順としては無い。memo から参照する形で AI は読めるが、現行ソースとの突き合わせや新旧比較の手順は未整備（§4-1）。利用側の実践を取り込む。

**Q14. 既存コードがある案件で /00 を実行したらどうなるか。**
既存コード（`app/` や intake-report.md）を検知して progress.md を作らず `/11-brownfield-intake` へ誘導する。/11 は as-is の逆起こしを行い、以後は /12 で差分駆動。

**Q15. リプレース後の新システムは別リポジトリにしたい。**
現状の /11 は同一リポジトリで既存コードを引き継ぐ前提。別リポジトリで新規開発する場合は、新規側はグリーンフィールド（/00〜）で進め、既存側の仕様は memo と docs への参照で渡す。リプレースプロファイル（§2-2 F）で正式化する。

### 運用・ガバナンス・コスト・セキュリティ

**Q16. ハーネスの更新はどう受け取るか。案件ごとの改変は消えるか。**
`/91-sync-from-harness`（人が `--apply`）。本体所有ファイル（エージェント・スキル・フック・テンプレート）は上書き、案件固有物（docs 実体・独自スキル・learnings）は触らない。本体所有ファイルを案件側で直接書き換えると次の同期で消えるので、変更は本体へ提案する。

**Q17. ソースや設計書が外部に送られることへの統制は。**
Claude Code の利用そのものは案件側の契約・設定に従う。ハーネス側は、外部反映（push・デプロイ・外部 API 書込）を ask / deny、秘密情報の書込を deny、MCP 等の接続追加を「信頼できない入力・機密データ・外部送信の 3 つを同時に持たない」規律で制限している。外部スキル・MCP は版固定とロック登録が必要。

**Q18. 費用の見通しと上限は。**
会話ごとの受領書で費用・ターン・コンテキスト使用率が残る（定価換算で請求額ではない）。ヘッドレス実行は `--max-turns` と `--max-budget-usd` の併用が規律。モデルと effort は役割別方針で固定し、案件側で勝手に変えない。

**Q19. Copilot でも使えるか。Claude Code との違いは。**
両対応（正は `.github/` 配下、Claude Code は生成されたアダプタ）。機械ガードの強さは環境で差がある（Claude Code は deny とフックの二重化、Copilot はフック）。Windows では Git Bash が必要。

**Q20. 導入の最初に何をすればよいか。**
(1) ハーネスを取得（テンプレート / ZIP / 同期 / 取り込み）、(2) `python tools/doctor.py` で配線確認、(3) memo を書く、(4) `/00-start-project`（既存コードがあれば /11 へ誘導される）。最初の 1 枚として「フェーズごとに人の関わり方が違う」を共有する。
