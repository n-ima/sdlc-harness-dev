# 手持ちメモ: ハーネスの現在地と方向性（2026-10-15 の整理）

意見交換会での説明用。所感への回答（別紙）に加えて、ハーネスの完成度・両対応・並列化について整理した内容。
根拠は本体（copilot-sdlc-harness v1.2.0、main 726ec98）の監査記録・評価レポートと、2026-10-15 の実走検証。

## 0. 評価の前提（方針として固定する）

このハーネスの目的は、会社で継続的に保守していくシステムの開発と運用に適用すること。評価はこの目的のもとで行う。

- 比較の単位は構築 1 回ではなく、構築・変更・引き継ぎ・監査・運用を含むライフサイクル。
- 小規模の単発や PoC は目的の外であり、そこで素の Claude Code に劣ることは欠点ではなく適用範囲の宣言（ハーネス自身も「使うべきでない場面」と明記）。
- すべてが実測できるわけではない。方針や考え方として置くものと、実測で裏づけるものを分けて記録する。実測が無いことは方針の無効を意味しない。留保は「どこまで実測済みか」の一言に留める。
- 利用者像は「エージェントを既に使う人」。判定の軸は案件・組織の条件で、ツールの習熟度は条件にしない。

### 方針として置くもの（実測に依らず正しいとする設計判断）

| 方針 | 理由 |
|---|---|
| 文書が記憶であり、会話は記憶ではない | 継続保守では担当とエージェントが入れ替わる。会話は残らず、文書だけが次の担当の入力になる |
| 変更は差分駆動で、要件 ID からテストとコードまで辿る | 保守の費用は「どこに影響するか」を調べる費用。これを機械で辿れることが保守の前提 |
| 完了は証拠で判定し、人は証拠を見る | 保守では人がコードを読まなくなる。読まない前提で安全にするには証拠しかない |
| 判断理由（ADR の捨てた選択肢・学習・決定記録）を副産物として残す | 引き継ぎで失われるのは「何を作ったか」ではなく「なぜそうしたか」 |
| 外部反映は人の承認を機械で強制する | 保守中の事故は外に出る操作で起きる。指示ではなく機構で止める |
| 要件定義で厚く聞く | 保守で高くつく欠陥は上流の曖昧さに由来する。ただし厚さは案件で選べるようにする（所感への対応） |

### 実測で裏づけるもの

- 変更局面の優位（評価課題の第 2 ステージで観測済み。n 小）
- 長期保守性・引き継ぎの費用（未実測。実案件で受領書と変更記録から採る）
- 要件定義の負荷（今回の実走と所感。標準プロファイル導入後に再計測）

## 1. 現在地の評価

自己評価 60 点は妥当。残り 40 点の大半は「分かっている種類の欠落」で、思想の誤りや構造の袋小路ではない。

| 軸 | 到達度 | 根拠 |
|---|---|---|
| 設計思想 | 世界の上位群 | 失敗モードごとに機構（フック・検証ツール・台帳）を対応させる方針。監査 4 回とも「思想の修正は不要」 |
| 機構の実装 | 7 割 | フック自己テスト sh 440 / ps1 412、CI 2 OS 緑（2026-09-10 に初めて）。指示任せのもの（矛盾検出・冒頭案内）と「1 面にしか適用されていない」ものが残る |
| 実運用での検証 | 4〜5 割 | 利用プロジェクト 3〜4 件。reviewer が実運用で 1 度も起動していない（2026-09-09 監査）。計測→振り返り→還流が一周していない。A/B は 10 走行すべて比較無効 |
| 人間側の使い勝手 | 3 割 | 開発者 1 人が回す前提。回答者・承認者の体験は未設計。今回の所感が外部からの初めての UX 信号 |
| 全体展開の準備度 | パイロット向け | チャンピオンが付く 2〜3 案件で使う段階 |

### 世の中との比較

- 機構の厳密さ（deny＋フック、証拠つき done、決定台帳、費用受領書、両ホスト対応、自己監査）は公開ハーネスにほとんど無い。残すべき固有資産はこの 5 つ。
- 製品としての完成度は Spec Kit（7 コマンド、clarify 5 問＋推奨、checklist、analyze）や Kiro（IDE 統合、EARS 3 ファイル）の後ろ。18 コマンド・40 超スキルで、利用者に中核の前提（フェーズごとに人の関わり方が違う）が伝わっていない。
- ホストの機能（/goal、agent teams、Workflow、routines、hooks の onFailure: block、Artifact）が自作領域を吸収しつつある。取り込みは遅れている。
- 構築 1 回の費用は高い（小規模の参考値で素の Claude Code の 3〜10 倍）。目的である継続保守の範囲では、変更と引き継ぎで回収してトータルで優位（§4-9）。小規模の単発は目的の外。
- 他ハーネスとの同一課題 A/B は未実施（評価装置に Spec Kit アームの下書きあり）。

### 監査を重ねても「これくらいは」の改善が残る理由

1. 監査の観点が「内部整合・セキュリティ・機械強制・計測」に偏り、人間側の使い勝手を観点に持っていなかった。
2. 成長ループの下流（/10 → /90 → /91）が実案件で一周していない。
3. 幅を広げすぎて「同じ事実を書く面」が増え、毎回「1 面にしか適用されていない」が出る。
4. 「厚く聞く」は n=1 の小さな題材での検証のまま配布された。今回の所感はその反証。
5. 推奨の明示・機能別分類・終了見通し・未決一覧・人向けレビュー観点は AI 以前の要件定義の常識。エージェントを縛る投資はしたが、人がどう使うかには投資していない。

## 2. やめるべきか

やめない。ただし「作り続ける」から「使わせて直す」へ。

- 乗り換え（Spec Kit / Kiro）では要件負荷は下がるが、機械強制・証拠・台帳・計測・自己監査を失い、結局作り直す。
- 今回の所感は、成長ループが外部に対して初めて機能した瞬間。価値仮説（大規模・曖昧・複数人で効く）を検証する唯一の経路。
- 即効修正（冒頭案内のテンプレート化、推奨の明示、行の分離、終了見通し、未決一覧）は数日規模。

続ける条件:
1. 機構を足すのをやめ、人間側（質問票・承認・設計書の読み方）に投資する。
2. 次の案件に出す前に短期修正 5 件とプロファイル選択（厚い／標準／軽量）を入れる。「厚い」のまま出すと同じ所感が返る。
3. 案件ごとに成功条件を先に決める（要件定義の人の作業が前回の半分、承認者が設計書を 30 分以内、要件起因の手戻り 0 件）。数字は受領書と stats で取れる。
4. 価値の判定は他組織の案件で行う（自分の案件は規模が違い反証にならない）。
5. やめる条件も決める: 標準プロファイルで 2〜3 案件試して負荷が下がらず「次も使いたい」が出なければ、要件フェーズは他ツールに委ね、コア（ガード・証拠・台帳・計測）だけに絞る。

懸念: 保守が 1 人。幅を広げる限り監査の指摘は減らない。残す 5 つを決め、それ以外はホストに委ねる判断を先にする。

## 3. 両対応（Claude Code / GitHub Copilot）

両対応は正しい（Copilot ライセンスしか無い組織が多い）。間違っているのは「どちらでも同じことができる」という目標。

- 同等性を守る限り、/goal・agent teams・Workflow・routines・Artifact は使えない。機械強制の強度も最初から違う（Claude Code は deny＋フック、Copilot はフックのみ）。
- 提案: 「同等」から「段階（Tier）」へ。
  - Tier 1（Claude Code）: ゲートを機械強制、自律区間を許可、並列実装を許可。
  - Tier 2（Copilot）: 指示層のみ。人のゲートがあるフェーズ（要件・設計）は同じ体験。全自動区間は「人がタスクごとに確認する直列」に縮退。リリース自動化は不許可。
  - 何が強制され何が助言かを対応表 1 枚で宣言し、分岐の設計判断を毎回しない。
- 強制の場所をエージェントのツール境界からリポジトリ境界へ寄せる: pre-commit と CI で validate-harness / trace-check / gate_status check / テンプレート文言の残存検査を回す。決定論ツール・docs 規約・状態機械はもともとホスト非依存。ホストのフックは早期警告に格下げ。
- AGENTS.md の標準化でアダプタ層は薄くなる。薄くなる層に投資しない。

## 4. 分割と並行

### 4-1. 人の関わる単位

- 「1 人が複数エージェントを動かす」に同意。律速はエージェント数ではなく人の判断帯域。
- 人の単位を 3 つに固定: 境界（分割・ICD・契約の変更）、受け入れ（証拠つき完了の承認）、昇格（3 回失敗・矛盾・外部反映）。それ以外は読まなくてよいと宣言する。
- 1 人起源の前提を洗い出す: 承認者 1 人、チャット 1 本、docs が唯一の記憶、「新しいチャットで /03」。複数人では役割分離（回答者・承認者・レビュアー）、同時編集、PR を人の単位にすることが要る。
- 規模差は機能追加で埋まらない。チーム形を 2〜3 個に決め（1 人＋エージェント群、PM 1 人＋2〜3 人、複数チーム）、中規模の実案件 1 本で試す。

### 4-2. 今の直列は構造に合っているか → 合っている

直列が守っているのは「ファイル衝突の回避」だけではない。

| 構造要素 | 直列との整合 | 並列で起きること |
|---|---|---|
| tasks.md / progress.md / notepad.md が唯一の状態 | 1 セッションが順に書く | 複数ワーカーの同時書き込みで競合。claim・所有権の欄が無い |
| タスクごと 1 コミット、単一ブランチ | 履歴がタスク順＝復旧点 | コミット交錯。worktree とマージ工程が未定義 |
| done 契約と証拠 | タスク単位で閉じる | 並列でも成立（強み） |
| 1 タスク 1 task-worker | context rot 対策 | 並列でも保たれる。直列の理由はコンテキストではない |
| 完了 10 タスクごとに reviewer | 直列の件数 | マージ済み件数で数え直す |
| retry → replan → escalate | 一本の流れ | 昇格が同時に来る。集約が要る |
| フック・受領書がセッション単位 | 1 セッション＝1 ループ | ワーカー単位の受領書の統合が無い |
| タスク間依存は順序に暗黙 | 前の結果を次が前提に | 依存欄が無いと並列可否を判断できない |

直列のまま失っているのは壁時計時間だけ。品質・追跡性は失っていない。

### 4-3. 実装フェーズに人のレビューは無い（訂正）

- 「人のレビュー帯域が詰まる」は一般論（Osmani の orchestration tax）で、このハーネスの実装フェーズには当てはまらない。実装〜テストは全自動区間。
- 実装中に人に届くのは 4 つだけ: 昇格、environment.md の人手作業、外部反映の確認、テスト後の受け入れ。
- 並列化の制約は人ではなく: (1) 統合の品質ループ、(2) 誤った境界の影響範囲（人がいない区間で N 本に同時波及、統合で初めて見つかる）、(3) 費用と予算。
- 人の帯域が効くのは実装の外側: 分割と ICD の承認、昇格への応答、リリース後の理解負債。docs・ADR・トレーサビリティを厚く残す理由はここ。
- 結論: 人のレビューを実装から外しているぶん、一般のチームより並列化に向いている。条件は、統合を独立工程にして小刻みに回す、分割の誤りが統合で機械的に見つかる、予算を系列単位で縛る、の 3 つ。

### 4-4. 向いているが、そのままでは駄目

- そのまま使える: 1 タスク 1 task-worker、done 契約と証拠、retry/replan/escalate、docs・ADR・トレーサビリティ、reviewer（起動条件だけ変更）。
- 足すもの:
  1. tasks.md に担当（claim）・書き込み範囲・依存の欄。範囲の重複を機械検査。
  2. ワーカーは worktree。状態と GATE は統合役だけが書く（単一書き手の原則を保つ）。
  3. 統合を独立工程に: 小刻みなマージ、全テスト、trace-check、reviewer をマージ件数で起動。
  4. 昇格はキューに積んで統合役が人へ。受領書はワーカー単位で合算。
  5. 系列単位の予算上限。
- やることは「直列をやめる」ではなく「統合役を 1 つ増やす」。

### 4-5. 構造は層を増やすのではなく implement の責務を変える

```
今（直列）
implement（1 つずつ配る・tasks.md と GATE を書く）
  └ task-worker → 完了 → 次の task-worker

提案（サブシステム内の並列）
implement = 統合役（配る・マージ・全テスト・trace-check・reviewer 起動・状態の唯一の書き手）
  ├ task-worker A（worktree A、書き込み範囲 A）
  ├ task-worker B（worktree B、書き込み範囲 B）
  └ task-worker C（worktree C、書き込み範囲 C）

大規模（サブシステム分割。large-scale-development の既存 2 層。未検証）
システム層の統合役（ICD と統合テスト。境界は人が承認）
  ├ サブシステム X の implement → ワーカー群
  └ サブシステム Y の implement → ワーカー群
```

- 統合役は専用のエージェント定義（例: integrator。git マージ・テスト実行・状態書き込みに限定、アプリコードは編集しない）にすると単一責務が守れる。
- サブシステム内の並列を先に実装して統合工程の形を固め、同じ統合役をシステム層に置く。

### 4-6. ホストの対応状況（公式ドキュメントで確認、2026-10-15）

- Claude Code: サブエージェントの入れ子は既定で 3 層まで（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`、1 で無効）。同時実行は既定 20（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）。定義に `isolation: worktree` で一時 worktree 実行（変更が無ければ自動片付け）。agent teams のチームメイトはセッションで、その下にサブエージェントを持てる。
- Copilot: runSubagent の入れ子は非対応という認識（PLATFORM.md も 1 段前提。導入時に再確認）。
- 含意: 層の構造はファイルと git で表現し（tasks.md の担当・範囲・依存、worktree、マージ工程は両ホスト共通）、自動起動だけホスト依存にする。Claude Code では統合役が自動起動、Copilot では人がワーカーのセッションを起動して統合役を兼ねる（Tier 2）。入れ子の深さは `invokes` と設定で 2 層に固定し、グラフを明示的に保つ。

### 4-7. 並列で開発効率は上がるか → 半分だけ正しい

- 上がる: 実装フェーズの壁時計時間。ただし N 倍ではなくクリティカルパスで決まる。基盤は直列、独立に走れるのはコアと周辺。中規模（独立タスク 10〜20）で 1.5〜3 倍程度、それ以下は統合工程で相殺。
- 上がらない: 費用（タスクあたり同じ＋統合分が増える。時間を買う手段で安くなる手段ではない）、案件全体の暦日（人のゲートの待ちで決まる。実走ではエージェント 45 分、残りは人の回答待ち）、品質（分割の誤りが同時波及する圧力。統合を小刻みに回さないと手戻りで食い戻す）。
- 小規模でも効く条件: 独立タスクが多い、1 タスクが長い（重いテスト・ビルド）、人が実装完了を待つ運用。タスク 10 個以下でほぼ直列依存ならライトパスの範囲で得るものはほぼ無い。
- 判断の仕方: 既存案件の tasks.md に依存欄を足し、クリティカルパス÷総タスク数で理論上の短縮率を出す（実装前に過去データだけで計算できる。PJ6 の 26 タスクなど）。
- 優先順位: 小〜中規模で効率に効くのは要件定義の負荷と承認の摩擦。並列化は統合工程の設計とセットで、大きい案件が見えた時点で入れる。

### 4-8. 肝は「どれだけ独立にできるか」。それは設計と実装計画で決まる

- 独立性を上げる手（/04・/05）:
  - 分割の軸を「書き込み所有権」にする。所有が重なる共通部分（スキーマ・共通部品）は先に直列で作り、扇形に広げる。
  - 境界を先に固定する。インターフェースと契約テストをタスクより先に書く。統合は「契約テストが通るか」に還元。
  - 縦割り（画面＋API＋データの 1 スライス）を基本にする。層で切ると全タスクが依存して並列にならない。
- 完璧を求めない代わりに持つもの:
  - 依存の明示（tasks.md の依存・書き込み範囲）。/05 で依存グラフを出す。
  - 測る数字: クリティカルパス÷総タスク数（事前）、統合時の衝突率・やり直し率（事後。次の分割の教訓＝成長ループの対象）。
  - 統合を安くする。独立性 8 割なら残り 2 割は統合で拾う前提。100% を狙って設計を歪めない。
- 注意: 並列のための分割と設計として正しい分割が一致する範囲で止める（人が境界を承認する意味がある箇所）。独立度は案件の性質に依存するので、並列を既定にせず /05 の数字で案件ごとに決める。
- ハーネスへの最初の変更: /05 に「依存グラフ・書き込み範囲・クリティカルパス」を必ず出させ、tools/ に並列度と範囲重複を機械検査する決定論スクリプトを 1 本置く。統合役を作る前に入れられ、既存案件で試算できる。

## 4-9. 今のハーネスは使えるか（訂正版）

前提: 利用者像は「エージェントを既に使う人」。判定の軸は案件・組織の条件だけで、ツールの習熟度は条件にしない。
ツールの知識が要る箇所は利用者の前提ではなく、ハーネスが塞ぐべき漏れとして扱う。

### 結論

使える。限定公開ベータの段階。「誰が」ではなく「どの案件に・どの体制で」を先に伝えれば使え、伝えずに配ると「使えない」と評価される。

### 根拠

- 要件定義〜アーキテクチャ設計まで実走で通り、各フェーズが設計どおりの様式で停止・再開した。本体にも両ホストの E2E 記録がある。
- 自己検証が常時動いている（フック自己テスト 852 件、CI 2 OS 緑）。
- Codex 監査（2026-08-31）が STOP とした 2 件（リリース承認規範の矛盾、権限集約）は 9 月に解消済み（D087）。残る open は CODEOWNERS 必須レビュー、A/B 再実施、英語入口、Copilot モデル方針の 4 件で、安全性に直結するものは無い。
- 進め方はエージェントが指示する。各フェーズの終わりに「次にやること」が 1 行で示され、人は呼ばれた場面（答える・承認する・外部反映を許可する）だけ関わる。案件の判断ができる人がいれば新規開発は回せる。

### 用途別の判定

| 用途 | 判定 | 条件・理由 |
|---|---|---|
| 中規模以上の新規開発 | ○ 使える | ゲートで判断できる人（業務と案件を理解している人）がいること。構築費は素の Claude Code の数倍だが、費用はライフサイクル全体で見る（下記「費用はライフサイクル全体で見る」の条件） |
| 開発者でない回答者・承認者を含む企業案件 | △ 使えるが重い | 質問票の負荷と設計書の分量が壁。短期修正（案内・推奨・行の分離・終了見通し・未決一覧）と「人の関わり方」の 1 枚を入れてから |
| 既存コードを引き継いで改修し続ける案件 | ○ 使える | /11 → /12 → /13 の経路がある。実案件での検証は薄い |
| 既存システムのリプレース（既存設計書あり） | × 未対応 | 既存設計書の取り込み・差異抽出・新旧テスト比較の手順が無い |
| 小規模の単発（単一機能・10 ファイル以下） | 対象外 | 目的（継続保守するシステム）の外。素の Claude Code より割高で遅いのは欠点ではなく適用範囲の宣言 |
| Copilot しか使えない組織 | △ 指示層のみ | 機械強制が弱い。要件・設計は同じ体験、全自動区間は人が確認する直列（Tier 2） |
| 自律リリースを含む無人運用 | × 設計上も不可 | 外部反映は人の承認が必須 |
| サンドボックス前提の高セキュリティ環境 | △ 多層防御のみ | Windows ネイティブに sandbox 層が無い |

### 人が把握すべき最小限（5 つ。これ以上は不要）

1. 段階で進み、人が呼ばれるのは「答える」「承認する」「外に出る操作を許可する」の 3 場面。
2. 許可の 1 ルール: プロジェクト内の編集・テストは許可。push・デプロイ・費用・データ削除・プロジェクト外は止まって読む。
3. 「新しいチャットで次を実行」は正常。成果はファイルに保存済み。渡された 1 行を貼る。
4. 「ブロックされました」は故障ではなく意図的な停止。表示された次の手順に従う。
5. 回答は質問票に書く。任意は空欄で「AI の案どおり」。必須だけ書く。

減らせない理解は 1 つだけ: ゲートでの判断（要件の承認、高影響の回答、技術選択）。これはツールの理解ではなく業務の理解で、人が関わる意味そのもの。

### ハーネスが塞ぐべき漏れ（利用者の前提にしない）

| 漏れ | 直し方 |
|---|---|
| 権限確認の文言が技術的（ツール名・コマンド） | 案件側 settings に編集・テストの既定許可を同梱し、ask を外部反映だけに絞る。表示文を「外に出ます: push」のように要約 |
| ブロック時に次の手順が無い | ブロックメッセージに必ず「次にやること」を付ける（セッション境界の固定様式と同じ発想） |
| 環境準備（Git Bash・Python・doctor） | 導入手順 1 枚と doctor の結果の読み方。回答者・承認者には不要 |
| Markdown の編集 | HTML フォームか Excel 往復 |
| 新しいチャットの意味が説明されない | 導入 1 枚に書く |
| 「フェーズごとに人の関わり方が違う」が伝わらない | 導入 1 枚の冒頭に置く |

### 「一般的に」と言い切れない理由（利用者側ではなく本体側の残作業）

- 外部の追試がゼロで、効果の証明（A/B）が統計的に成立していない。
- 導入教育（最初の 1 枚）が無い。
- 案件種別で入口を選べず、厚い要件定義が既定。
- 保守が 1 人で、利用者が増えたときの対応余力が無い。

### 費用はライフサイクル全体で見る

「素の Claude Code の数倍」は構築 1 回分の比較で、評価の単位としては狭い。費用は構築・変更・引き継ぎ・監査・ハーネス自体の運用の 5 つで見る。

| 局面 | 素の Claude Code（文書なし） | 本ハーネス | 根拠の強さ |
|---|---|---|---|
| 構築 | 安い・速い（小規模で 1/3〜1/10） | 高い。要件定義の人の作業が最大の費目 | 実測あり（参考値） |
| 変更（運用中の改修） | 変更のたびにコードを読み直す。矛盾は実装後に見つかる。回帰テストは促されて初めて行う | /12 が要件 ID から設計・タスク・テスト・コードを辿り、該当部分だけ再ゲート。回帰は規律として強制 | 評価課題の第 2 ステージで観測（n 小） |
| 引き継ぎ・担当変更 | コードとチャット履歴（30 日で消える）しか残らない。前任の判断理由は失われる | requirements / ADR（捨てた選択肢つき）/ environment / learnings / 決定記録が残り、新しい担当も新しいエージェントも同じ文書から始められる | 構造上の論拠。長期の実測は未 |
| 監査・説明責任 | 後から文書を起こす | トレーサビリティ・証拠つき完了・受領書が最初から残る | 構造上の論拠 |
| ハーネス自体の運用 | 無し | 本体の更新取り込み（/91）、docs の鮮度維持（/13 で乖離検出）、案件ごとの学習コスト | 実運用で未計測 |

結論: 下記の条件のもとでは、トータルで素の Claude Code より優位。構築で払う差額を変更と担当交代で回収する。構造上そうなり、変更局面は評価課題でも観測済み。相手先に出すときの留保は「構造上の優位。実測は変更局面まで、長期は未」の一言だけでよい。

ハーネスが費用で有利になる条件:

- システムの寿命が 1 年を超え、運用中の変更が繰り返し発生する
- 担当の交代や複数人の関与が見込まれる（引き継ぎのたびに文書を起こし直さない）
- 要件が曖昧で、矛盾や仕様漏れを実装後に見つけると高くつく
- 監査・説明責任（なぜその設計か、何を検証したか）が求められる
- 同じ組織で案件を繰り返す（学習コストと規約スキルが次の案件に転用される）

逆に、使い捨て・PoC・単発スクリプト・寿命の短いツールは、構築の差額を回収できないので使わない。

補足（言い方の訂正）:
- 文書の作成と更新はエージェントの仕事で、人の負担ではない。人がやるのは「変更はハーネスのセッションから頼む」だけ。乖離が起きるのはハーネスの外（別ツール・IDE）で直接変えたときに限られ、/13 が検出する。
- ハーネスの価値は「上流文書がある」ことではない（それは何を使っても作る）。価値は (1) 文書がエージェントの入力そのものであること、(2) 変更のたびに AI が文書を同期し、要件 ID でテストとコードまで結ばれていること、(3) 判断理由（ADR の捨てた選択肢・learnings・決定記録）が副産物として残ること。
- 正しい比較相手は「文書はあるが AI と結びついておらず、リリース後に同期されない従来の工程」。差が出るのは変更と引き継ぎの局面。既に上流文書を厳密に維持できている組織では増分価値は小さく、残るのは AI が読んで更新しトレーサビリティを機械検査する点。
- 長期の実測はまだ無い（構造上の論拠）。

### 位置づけ

Spec Kit や Kiro が「軽く始めて足りない分を人が補う」道具なのに対し、このハーネスは「重く始めて機械の縛りで守る」道具。曖昧で長期で複数人の案件に合い、それ以外には合わない。この線引きを先に伝えることが「使える」の条件。

## 5. 一言で

- 両対応は「同等」から「段階」へ、強制はリポジトリ境界へ。
- 並行は「完璧な分割」ではなく「違反が機械的に見える分割」へ。統合役を 1 つ増やす。
- 人の単位は「読む量」ではなく「判断の列」へ。
- 方向転換ではなく焦点の移動。機構を足すのをやめ、人間側と成長ループの一周に投資する。
