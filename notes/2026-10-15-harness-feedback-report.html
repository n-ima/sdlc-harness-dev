0. 結論

評価の前提: このハーネスの目的は、会社で継続的に保守していくシステムの開発と運用に適用すること。評価はこの目的のもとで、構築 1 回ではなく構築・変更・引き継ぎ・監査・運用のライフサイクル全体で行う。小規模の単発や PoC は目的の外。すべてが実測できるわけではないので、方針として置く設計判断と実測で裏づける項目を分けて記す。

所感の「質問が終わらない」「量が多い」「成果物が膨大」はすべて実機で再現した。いずれも個別の不具合ではなく、設計思想（要件定義で厚く聞く、独立レビューの指摘から追加質問を派生させる、回数と分量に上限を置かない）から構造的に生じる。一方、回答候補・保留の吸収・矛盾の検出・差分駆動の遡及・既存コードの取り込み・保守の役割分担は実装済みで、所感との差は「推奨の明示」「機能別の分類」「課題一覧の見せ方」「リプレース型の手順」「人が見る観点」に絞られる。

3. HTML で人が確認する方法

「md をエディタで読んで承認する」運用は、開発者でない回答者・承認者には最初の壁になる。想定される質問は「確認は HTML でできないか」「質問票も HTML で答えられないか」の 2 つ。本ハーネスには既に HTML を使う箇所が 2 つあり、その延長で実現できる。

既にある HTML（1）画面モック

ui-design-mockup スキルは、CDN 無しの自己完結 HTML を 1 画面 1 ファイルで作り、人はブラウザで開いて確認、修正は「チャットで指示」か「HTML を直接編集して返す」の 2 経路。承認は設計ゲートの一部。閲覧にトークンは掛からない。

既にある HTML（2）説明ページの生成

tools/gen-docs.py が prompts/skills/agents の一次データから .github/harness/*.html（overview・agents・skills・commands・guardrails・internals）を生成している。「同じ事実を書いた複数の面」を手編集でなく生成で揃える原則（N 面鏡の生成物化）。

回答案

  • 確認（承認）は HTML でできる。 承認対象のフェーズごとに「レビューパック」を自己完結 HTML で生成する。中身は 1 分サマリ、人の確認観点（Q12 の 4 点など）、未決一覧、spec-critic の指摘と対応、前回承認からの差分。承認・差し戻しのボタンは「承認文をクリップボードにコピーする」だけにし、ゲートの書き換えは従来どおりチャットの明示発言で行う（承認バイパスを作らない）。
  • 質問票も HTML で答えられる。 questionnaire.py に html サブコマンドを足し、質問票 md から入力フォーム付き HTML を生成する。回答はフォームの「md を書き出す」ボタンで回答欄を埋めた md をダウンロードして上書きする（正は md のまま）。複数人の分担は §5 を参照。
  • Claude Code 側の最新機能も使える。 Claude Code の Artifact 機能（デスクトップ／Web）は HTML ページを非公開リンクとして公開し、コメントを Claude に戻せる。社内で共有リンクを許容できる案件では、レビューパックを Artifact として公開し、承認者はブラウザでコメントする運用が可能（ハーネスは CDN 無しの自己完結 HTML を作るので、そのまま公開できる）。2026-10 の更新では routines（定期実行）の結果も Artifact として公開される。
  • やらないこと。 HTML を正にしない（md と二重管理になる）。承認ボタンで GATE_STATUS を直接書かない。外部 CDN に依存しない（オフライン・社内 PC で開ける）。

5. 複数人で並行して行う方法

所感の背景（複数人の回答者、工程ごとの検収）から、「複数人で同時に進められるか」が問われる。本ハーネスは単一セッション・単一承認者を前提に作られているが、並行の単位ごとに既存の仕組みがある。

  • A（人の並行）: 質問票の分類（または Q4 の機能キー）ごとに担当を割り当てる。担当列と状態列を questionnaire.py の Excel 書き出し／取り込み（§3）で持つ。回答は 1 つの md に戻し、承認者は 1 人に固定する（ゲートの明示承認はユーザーの発言で記録される設計）。
  • B（成果物の並行）: large-scale-development スキルがシステム層／サブシステム層の 2 層に分け、分割と ICD は人が承認、内側は AI。サブシステムごとに docs とセッションを分ける。
  • C（エージェントの並行）: worktree 単位で task-worker を並列に走らせる。Claude Code の agent teams は 2026-02 に実験機能として追加（既定オフ、セッション再開不可などの制約）。本ハーネスの deny／フックは cwd 単位で効くため、worktree ごとに同じ設定が読まれることを doctor.py で確認する手順を足す。

6. 画面設計で Figma と連携する方法

現状のハーネスは自己完結 HTML のモックだけで、Figma との連携は無い（指示層に figma の語は無い）。Figma 公式の MCP サーバー（https://mcp.figma.com/mcp。リモート版は全プランで利用可）を使うと、次の 2 方向が可能になる。

  • 経路 1（デザイナーの Figma を正にする）: 要件定義の「画面横断の仕様」と /04 の詳細設計で、Figma のフレーム URL を memo／docs に書く。design エージェントは MCP でレイアウト・トークン・コンポーネントを読み、HTML モックの代わりに Figma を参照して design-tokens.md を生成する。Code Connect の対応表があれば実装は既存コンポーネントを使う。
  • 経路 2（AI の HTML モックを Figma に送る）: ui-design-mockup が作った HTML を code-to-canvas で Figma に送り、デザイナーが Figma で手直しし、経路 1 で戻す。HTML と Figma の二重管理を避けるため、合意後は一方を正にする。
  • 導入手順（ハーネスの規律）: MCP の追加は AGENTS.md の Lethal Trifecta 判定（信頼できない入力・機密データ・外部送信の 3 つを同時に持たない）と、external-lock.json への出所・版の登録が必要（未登録は validate が ERROR）。Figma MCP は書込（canvas への生成）を持つため、設計フェーズのセッションだけに接続し、実装・リリースのセッションでは外す。接続例: claude mcp add --transport http figma https://mcp.figma.com/mcp（公式ドキュメントで最新の手順を確認する）。
  • 直す場所: ui-design-mockup/SKILL.md に「Figma を正にする場合」の節、design.agent.md 手順 5.5 に経路の選択、skill-authoring の外部 MCP 登録手順に Figma の例を追加。

7. 対策の全体像（全体展開を見据えて）

所感が示すのは 2 点。最新版でも「要件定義の負荷が高い」こと、そして利用側の文脈（リプレース、Excel で回る業務、複数人の回答者、検収文化）はハーネスの目的である「継続的に保守するシステム」の範囲内なのに、出発点が 1 人の新規開発だったために必要な部品がまだ無いこと。今回のギャップは対象外の使われ方ではなく、埋めるべき対象。個別の手直しに加えて、入口を案件種別で選べる構成にする。

時期内容所感との対応
短期（数週間）テンプレート冒頭文／推奨の明示／高影響への候補／回答者向け行と AI 向け行の分離／終了見通し／機能別分類／台帳の状態列と未決表示／レビューパック（md 版）Q1〜Q7、Q12
中期（1〜2 か月）標準プロファイル（上位 N 問＋推奨採用）／ラフモック前倒し／決定表・状態遷移表・テスト草案の前倒し・未カバー検査／レビューパック HTML・質問票 HTML・Excel 往復／フックの onFailure: block 採用の検討Q1、Q8、Q9、§3、§5
長期（四半期）コア＋プロファイル再編／リプレース入口／Figma 経路／/goal を done 契約から生成して全自動区間に適用／Workflow による並列化／プロファイル別の計測（要件工数・設計差し戻し率・要件起因の手戻り）Q10、§4、§6

採らない案: リプレース専用ハーネスを別リポジトリで作ること。保守線が 2 本になり、ガード・検証・成長ループを二重に持つ。全体展開で効くのは「入口の選択肢」であって「ハーネスの本数」ではない。Spec Kit 等の他ハーネスは「置換」ではなく「参照」として使い、同一課題での比較（本体の評価装置に Spec Kit アームの下書きあり）で判断する。

進め方・要件定義

Q. 質問票を複数人で分担して回答できるか

できる。分類ごとの見出しで担当を割り当てる。担当列・状態列は無いので、冒頭に担当表を書くか Excel 書き出し（§3・§5）を待つ。回答は必ず同じ md に戻す。チャットで答えた分も転記される。

Q. 回答を数週間止めても大丈夫か

大丈夫。/02 は会話履歴でなく質問票ファイルだけを読む設計で、別の日・別のチャットで再開できる。再開は新しいチャットで /02-requirements-deepdive。

Q. memo にはどこまで書けばよいか

書くほど質問が減る。「memo と探索で分かることは質問しない」規律なので、既存資料・業務フロー・画面一覧・制約（環境・権限・締め処理）を貼るか参照パスを書く。被覆表で Clear の分類は質問されない。実走では memo 18 行から 85 問が出た。

Q. 要件定義にどれだけ時間と費用がかかるか

実走（7 人向け小規模アプリ）で /00〜/02 承認まで AI 側 38 分・$10.1、人は 85 問＋チャット 12 問。業務システムではこの数倍。費用は会話ごとの受領書（/99-status）で見られる。

Q. 要件の「承認」は何を見て行うか

requirements.md（ユーザーストーリーと受け入れ条件）・nfr.md・environment.md・未確定事項台帳。見るべきは「スコープ外が書かれているか」「高影響を自分で決めたか」「未決が設計を左右しないか」。文言の検証は spec-critic が済ませている。

Q. 承認後に要件を変えたくなったら

構築中なら該当フェーズへ差し戻し（要件なら /02）。運用中なら /12-change-request。どちらも影響範囲をトレーサビリティ表から辿って該当部分だけ再ゲートする。

設計・画面

Q. 画面デザインは誰が決めるか。デザイナーの成果物を使えるか

設計フェーズで AI が HTML モックを作り、人が目視で直す。Figma を正にする場合は §6 の経路 1。既存のデザインがあれば memo か docs に置けば参照される。

Q. 設計書が膨大で読めない

Q12 の 4 点（技術スタックと ADR・コンテキスト図・NFR 実現方法・要件対応表）だけ見る。残りは spec-critic の指摘と対応結果を読む。承認時のレビューパック（§3）で 1 画面に要約する。

Q. 技術スタックは指定できるか。社内標準に縛れるか

できる。memo か environment.md に必須技術・禁止技術を書けば制約として扱われる。設計で候補提示があるときに選ぶ。社内規約は stack-conventions スキルとして案件側で作り再利用する（同期で上書きされない）。

実装・テスト

Q. 実装中は本当に何も見なくてよいのか

設計承認後からテスト完了までは全自動区間。止まるのは、要件・設計から判断できない事実が要るとき、同一タスク 3 回失敗、push・デプロイ等の外部反映、environment.md で「人手」に分類した作業。完了は証拠で判定し、10 タスクごとに独立レビューが入る。

Q. 既存のテスト仕様書の形式（Excel）で出せるか

正は docs/04-test/test-plan.md（Markdown 表）。Excel への変換は案件側のスクリプトで可能だが正は md のまま。要件×ケースのマトリクス（Q9）を追加予定。

Q. テストの網羅性は誰が保証するか

現状は AI（要件 ID 紐づけ＋観点チェックリスト）と reviewer。人の承認工程は無い。Q9 の対策で「テスト設計の承認」を 1 回入れる。

既存システム・リプレース

Q. 既存の設計書（Word/Excel）を読ませられるか

手順としては無い。memo から参照すれば AI は読めるが、現行ソースとの突き合わせや新旧比較は未整備（Q10）。貴社の実践を取り込みたい。

Q. 既存コードがある案件で /00 を実行したら

既存コード（app/ や intake-report.md）を検知して progress.md を作らず /11-brownfield-intake へ誘導する。/11 は as-is の逆起こしを行い、以後は /12 で差分駆動。

Q. リプレース後の新システムは別リポジトリにしたい

現状の /11 は同一リポジトリで既存コードを引き継ぐ前提。別リポジトリなら新規側はグリーンフィールド（/00〜）で進め、既存側の仕様は memo と docs への参照で渡す。リプレースプロファイル（§7）で正式化する。

運用・ガバナンス・コスト・セキュリティ

Q. ハーネスの更新はどう受け取るか。案件ごとの改変は消えるか

/91-sync-from-harness（人が --apply）。本体所有ファイルは上書き、案件固有物（docs 実体・独自スキル・learnings）は触らない。本体所有ファイルを案件側で直接書き換えると次の同期で消えるので、変更は本体へ提案する。

Q. ソースや設計書が外部に送られることへの統制は

Claude Code の利用自体は案件側の契約・設定に従う。ハーネス側は、外部反映（push・デプロイ・外部 API 書込）を ask/deny、秘密情報の書込を deny、MCP 等の接続追加を Lethal Trifecta の規律で制限する。外部スキル・MCP は版固定とロック登録が必要。

Q. 費用の見通しと上限は

会話ごとの受領書で費用・ターン・コンテキスト使用率が残る（定価換算）。ヘッドレス実行は --max-turns と --max-budget-usd の併用が規律。モデルと effort は役割別方針で固定する。

Q. Copilot でも使えるか

両対応（正は .github/ 配下、Claude Code は生成アダプタ）。機械ガードの強さは環境で差がある。Windows では Git Bash が必要。

Q. ループエンジニアリング／グラフエンジニアリングに対応しているか

§4 のとおり。ループの要素（スキル・サブエージェント・状態・停止条件・独立検証）は実装済みで、/goal 相当の「検証可能な停止条件を別モデルが判定する」仕組みは未導入。グラフは状態機械とハンドオフが暗黙のグラフで、ノード／エッジの型とチェックポイントの明示は未。

Q. 導入の最初に何をすればよいか

(1) ハーネスを取得（テンプレート／ZIP／同期／取り込み）、(2) python tools/doctor.py で配線確認、(3) memo を書く、(4) /00-start-project（既存コードがあれば /11 へ誘導）。最初の 1 枚として「フェーズごとに人の関わり方が違う」を共有する。
